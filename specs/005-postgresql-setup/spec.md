# Feature Specification: PostgreSQL導入

**Feature Branch**: `005-postgresql-setup`  
**Created**: 2026-01-30  
**Status**: Draft  
**Input**: User description: "PostgreSQLを導入"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 開発環境でのデータベース接続 (Priority: P1)

開発者として、ローカル環境でPostgreSQLデータベースに接続して、ワークアウトデータを永続化できるようにしたい。これにより、アプリケーションがステートレスなインメモリストレージから本格的なデータ永続化層に移行できる。

**Why this priority**: データ永続化はOPTelの基本機能であり、すべての他の機能（ワークアウト記録、プログラム管理など）の基盤となるため最優先。

**Independent Test**: Docker Composeでデータベースを起動し、アプリケーションからCRUD操作が正常に動作することを確認することで独立してテスト可能。

**Acceptance Scenarios**:

1. **Given** Docker Composeが設定されている, **When** `docker compose up -d postgres`を実行, **Then** PostgreSQLコンテナが起動し、接続を受け付ける状態になる
2. **Given** PostgreSQLが起動している, **When** アプリケーションを起動, **Then** データベースに正常に接続し、ヘルスチェックが成功する
3. **Given** アプリケーションがDBに接続している, **When** ワークアウトデータを作成・読み取り・更新・削除, **Then** データが正しく永続化・取得される

---

### User Story 2 - データベーススキーマの初期化 (Priority: P2)

開発者として、CLIコマンドでデータベーススキーマを適用できるようにしたい。これにより、スキーマ変更を明示的に管理し、意図しない変更を防げる。

**Why this priority**: スキーマ管理は開発効率に直接影響し、データ永続化の次に重要なため、P2とする。

**Independent Test**: 空のデータベースに対してアプリケーションを起動し、必要なテーブルが作成されていることを確認することで独立してテスト可能。

**Acceptance Scenarios**:

1. **Given** 空のPostgreSQLデータベース, **When** `make migrate`を実行, **Then** 必要なテーブルとインデックスが作成される
2. **Given** 既存のスキーマがある状態, **When** 新しいマイグレーションを実行, **Then** スキーマが適切に更新され、既存データが保持される

---

### User Story 3 - テスト用データベース環境 (Priority: P3)

開発者として、統合テスト用の独立したデータベース環境を持ちたい。これにより、テストが本番・開発データに影響を与えることなく実行できる。

**Why this priority**: テスト環境の分離は品質保証に重要だが、初期段階では開発用データベースをテストにも使用可能なため、P3とする。

**Independent Test**: テストスイートを実行し、テスト用データベースが使用され、テスト後にクリーンアップされることを確認することで独立してテスト可能。

**Acceptance Scenarios**:

1. **Given** テスト実行環境, **When** 統合テストを実行, **Then** Testcontainersにより一時PostgreSQLコンテナが起動され、開発用データベースに影響しない
2. **Given** テストが完了した状態, **When** 次のテストスイートを実行, **Then** 新しい一時コンテナが起動され、前回のテストデータの影響を受けない

---

### Edge Cases

- データベース接続が失敗した場合はどうなるか？ → Exponential Backoffで最大5回リトライし、それでも失敗した場合は適切なエラーメッセージを返す
- マイグレーション中にエラーが発生した場合はどうなるか？ → トランザクションがロールバックされ、エラーログが出力される
- データベースのディスク容量が不足した場合はどうなるか？ → 適切なエラーをログに記録し、アラートを発する準備をする

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムはPostgreSQLデータベースに接続できなければならない（接続失敗時はExponential Backoffで最大5回リトライ）
- **FR-002**: システムは環境変数を通じてデータベース接続設定を構成できなければならない
- **FR-003**: システムはデータベース接続のヘルスチェックエンドポイントを提供しなければならない
- **FR-004**: システムはデータベースマイグレーションをCLIコマンド（`make migrate`など）で手動実行できなければならない
- **FR-005**: システムはコネクションプーリング（開発環境では最大10接続）を使用してデータベース接続を効率的に管理しなければならない
- **FR-006**: システムはデータベースエラーを適切にログに記録しなければならない
- **FR-007**: 開発環境用にDocker Composeでデータベースを起動できなければならない
- **FR-008**: テスト環境ではTestcontainersを使用して独立した一時PostgreSQLコンテナを起動しなければならない

### Key Entities

- **Database Connection**: データベースへの接続設定（ホスト、ポート、ユーザー、パスワード、データベース名）
- **Migration**: スキーマ変更を管理するバージョン管理されたファイル
- **Connection Pool**: 効率的なデータベースアクセスのための接続プール

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 開発者は3分以内にローカル開発環境でデータベースを起動し接続できる
- **SC-002**: アプリケーション起動からデータベース接続確立まで10秒以内に完了する
- **SC-003**: データベースヘルスチェックが正常な状態では100%成功する
- **SC-004**: マイグレーションは既存データを破壊することなく適用できる
- **SC-005**: 統合テストは独立したテストデータベース環境で実行され、テスト間の干渉がない

## Clarifications

### Session 2026-01-30

- Q: 開発環境で使用するPostgreSQLのバージョンは？ → A: PostgreSQL 17（17.x系）
- Q: テスト用データベースの分離方式は？ → A: Testcontainers（テスト実行時に一時コンテナを起動）
- Q: コネクションプールの最大接続数は？ → A: 開発環境では10接続
- Q: マイグレーション実行タイミングは？ → A: CLIコマンドで手動実行（`make migrate`など）
- Q: 接続失敗時のリトライ戦略は？ → A: Exponential Backoff（指数バックオフ、最大5回）

## Assumptions

- PostgreSQL 17.xをDockerコンテナとして開発環境で実行される
- 接続設定は環境変数で管理される（12-factor app原則に従う）
- マイグレーションツールはGoエコシステムの標準的なものを使用する
- 本番環境のデータベース設定は本スペックの範囲外とする
