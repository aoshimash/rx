# Domain Model

## Three-Tier Training Lifecycle

```
Program → Plan → Log
```

1. **Program** — A reusable training template containing sessions with exercises and prescribed weights. Programs have no lifecycle status — they are static templates that can be used repeatedly. Can be created manually, imported from JSON, or generated by AI.
2. **Plan** — The user's working document: an ordered queue of upcoming sessions to execute. A Plan is created by expanding a Program (or adding sessions manually). Each user has at most one active Plan.
3. **Log** — A record of one training session actually performed. Optionally linked to a Program and session name for tracking which prescription was followed.

## Key Concepts

### Program

A **Program** is a reusable training template. It:

- Contains **ProgramSessions** (named workout days with an order and optional date)
- Each session has **ProgramSessionEntries** (exercises with prescribed weights)
- Optionally organizes sessions into **ProgramGroups** (hierarchical, max 2 levels deep — e.g., Block → Week)
- Has no lifecycle status — Programs are inert templates, not stateful entities

### Plan

A **Plan** is the user's execution queue. It:

- Contains **PlanSessions** — concrete workout prescriptions the user intends to perform
- Is populated by expanding a Program (copies sessions into the Plan) or by adding sessions manually
- Each user has at most one Plan (singleton per user)
- Sessions can be removed individually as they are completed or skipped

### Log

A **Log** records what was actually performed in one training session. A Log **optionally** references a Program (`program_id`) and a session name (`session_name`), enabling tracking of which program session was performed. Logs without a `program_id` represent unplanned/ad-hoc training sessions.

## Entity Relationships

```
┌───────────────────┐     ┌──────────────────────┐
│     Program       │────►│   ProgramSession      │  (named training day)
│  (reusable        │     └──────────┬───────────┘
│   template)       │               │
│                   │     ┌──────────▼───────────┐
│                   │     │ ProgramSessionEntry   │  (exercise with load_kg)
└────────┬──────────┘     └──────────────────────┘
         │
         │ expand into
         ▼
┌───────────────────┐     ┌──────────────────────┐
│      Plan         │────►│    PlanSession        │  (concrete workout to do)
│  (1 per user)     │     └──────────┬───────────┘
└───────────────────┘               │

                            │  PlanSessionEntry   │  (exercise prescription)
                            └────────────────────┘

┌───────────────────┐
│       Log         │  (record: what was actually performed)
│  program_id (opt) │
│  session_name     │
└───────────────────┘
```

### Program Groups

Programs can optionally organize sessions into a hierarchy using **ProgramGroups** (max 2 levels deep):

```
Program
├── Group: "Block A"
│   ├── Group: "Week 1"
│   │   ├── Session: "Day 1"
│   │   └── Session: "Day 2"
│   └── Group: "Week 2"
│       ├── Session: "Day 1"
│       └── Session: "Day 2"
└── Session: "Deload" (ungrouped)
```

Groups are purely organizational — they carry no business logic. The API enforces max depth of 2 levels.

## Design Decisions

- **ProgramSession is a DB entity** — Sessions are first-class entities with IDs, ordering, and optional dates
- **Program has no status** — Programs are reusable templates; execution state lives in Plan and Log
- **Plan is a singleton per user** — Simplifies the "what's next?" question
- **Log.program_id is optional** — Supports both program-linked and ad-hoc training sessions
- **Flexible metadata** — Domain-specific data like RPE, tempo, rest time is stored in the `metadata` JSON field rather than dedicated columns, following the "Dumb Backend" philosophy
